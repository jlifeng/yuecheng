# 悦程 V1 设计文档

## 1. 文档目标

本文档用于固化 `悦程` 项目的 V1 设计方案，作为后续实现计划、页面设计、后端接口设计和数据建模的统一依据。

本文档聚焦：

- 完整平台 V1
- 小规模真实商用版
- 商务车接待场景
- 平台撮合，不介入线上支付

本文档不覆盖：

- 详细数据库 DDL
- 详细接口定义
- 具体技术实现代码
- 超大规模运营体系

## 2. 产品定位与范围

`悦程` 是一个面向商务接待和商务包车场景的供需撮合平台，核心目标是解决非标商务用车场景下的高效匹配、方案比选、履约跟踪和交易留痕问题。

平台采用以下业务模式：

- 乘客发布需求单
- 商家围绕需求单提交报价与方案摘要
- 乘客比选后确认服务商
- 商家指派司机执行服务
- 平台记录履约过程、费用明细、发票流转和异常处理

V1 包含以下四个业务面：

1. 乘客端小程序
2. 商家端小程序
3. 平台管理后台
4. 平台后端与数据层

V1 明确不做以下能力：

- 在线支付
- 平台担保交易
- 分账结算
- 独立的第二套“车找人”交易模型
- 复杂会员、优惠券和营销体系
- 完整仲裁/申诉中心
- 复杂商家装修系统
- 重型 PC 商家后台

## 3. 核心设计原则

### 3.1 单一交易内核

平台只保留一套交易内核，即 `乘客需求单`。

即使前台保留“车找人”展示能力，其本质也只是商家运力展示和线索入口。真正进入报价、选单、履约、费用确认和发票流转的，统一回到乘客需求单模型。

### 3.2 平台撮合，不介入支付

平台只做信息撮合、过程记录和交易留痕：

- 不在线收款
- 不代付
- 不做分账
- 所有费用线下结算

但平台必须保留可追溯的费用记录，包括报价金额、附加费明细、最终总额和确认记录。

### 3.3 商家为服务责任主体

司机执行服务，但平台视角中的责任主体始终是商家。商家负责：

- 入驻与资质
- 报价提交
- 司机指派
- 费用录入
- 发票上传
- 异常协同

### 3.4 小规模真实商用优先

V1 要求真实可用，而不是纯演示原型。因此后台审核、异常留痕、封禁能力、费用确认和发票流转都必须纳入首版。

## 4. 角色体系

### 4.1 乘客

主要职责：

- 发布需求
- 查看商家报价
- 比较价格、评分和方案摘要
- 选择商家
- 查看履约进度
- 确认费用留档
- 下载发票
- 提交评价
- 发起异常报备

### 4.2 商家管理员 / 车队队长

主要职责：

- 提交入驻申请
- 维护商家主页和资质
- 管理车辆与司机
- 浏览需求单
- 提交报价
- 指派司机
- 跟进履约
- 录入费用明细
- 上传发票
- 处理异常协同

### 4.3 普通司机

主要职责：

- 查看被指派订单
- 执行履约动作
- 更新关键状态节点
- 提交必要备注

权限限制：

- 不可独立入驻
- 不可修改商家主页
- 不可提交对外报价
- 不可管理车辆和成员权限

### 4.4 平台审核/运营人员

主要职责：

- 审核商家入驻资料
- 监管用户和商家状态
- 处理异常和投诉记录
- 执行警告、限制、封禁
- 维护基础配置

### 4.5 平台超级管理员

主要职责：

- 管理后台权限
- 管理高权限配置
- 管理系统级监管能力

## 5. 业务范围与主链路

平台完整主链路如下：

`商家入驻审核通过 -> 乘客发布需求单 -> 商家报价 -> 乘客比选确认 -> 商家指派司机 -> 司机执行履约 -> 商家录入费用明细 -> 乘客确认留档 -> 商家上传发票（如需）-> 乘客下载发票 -> 双方评价 / 平台处理异常`

主链路拆分为四个阶段：

### 5.1 准入阶段

- 乘客轻注册进入平台
- 在关键节点补充实名联系人信息
- 商家提交入驻和资质资料
- 后台审核通过后商家才可报价和接单

### 5.2 撮合阶段

- 乘客按主单型发布需求
- 系统开放动态报价窗口
- 多商家提交“价格 + 方案摘要”
- 乘客排序比选并确认一家商家

### 5.3 履约阶段

- 商家接单并指派司机
- 司机更新关键节点状态
- 乘客查看过程状态和联系方式
- 双方可提交异常报备

### 5.4 收尾阶段

- 商家录入最终费用明细
- 乘客确认费用留档
- 商家上传发票
- 乘客下载发票
- 双方评价
- 平台归档异常处理结果

## 6. 主单型设计

V1 统一收敛为三类主单型：

### 6.1 接送类

适用场景：

- 接机
- 送机
- 接站
- 送站
- 点对点商务接待

### 6.2 包时/包天类

适用场景：

- 半日包车
- 全日包车
- 会务接待
- 城市内多点接驳

### 6.3 多日行程类

适用场景：

- 多日商务接待
- 连续多天包车
- 巡回接待

这三类主单型共享统一交易模型，但在需求字段、报价说明和履约描述上允许轻微差异。

## 8. 数据模型与状态机

V1 建议围绕以下核心实体建模：

1. 用户
2. 商家主体
3. 司机
4. 车辆
5. 需求单
6. 报价单
7. 订单
8. 履约记录
9. 费用明细
10. 发票记录
11. 评价记录
12. 异常记录

### 8.1 需求单

需求单是唯一交易起点，负责承载撮合阶段。

建议状态：

- `draft`
- `published`
- `bidding`
- `quoted_closed`
- `confirmed`
- `cancelled`
- `expired`

### 8.2 报价单

报价单由商家针对需求单提交。

建议状态：

- `submitted`
- `updated`
- `selected`
- `rejected`
- `expired`
- `withdrawn`

关键字段建议至少包括：

- 需求单 ID
- 商家 ID
- 报价金额
- 推荐车型
- 可承载人数/行李说明
- 服务说明
- 报价有效期
- 商家评分和展示快照

### 8.3 订单

订单负责成交后的履约与收尾阶段。

建议状态：

- `pending_assign`
- `assigned`
- `on_the_way`
- `arrived_pickup`
- `waiting_passenger`
- `passenger_boarded`
- `arriving_destination`
- `arrived_destination`
- `pending_fee_confirm`
- `completed`
- `cancelled`
- `abnormal_processing`

`waiting_passenger` 为商务接待场景关键状态，必须保留。

### 8.4 履约记录

履约记录不只是日志，而是具备业务语义的过程节点。

建议节点类型：

- 出发前往接驾
- 到达起点
- 开始等待
- 结束等待
- 乘客上车
- 到达终点
- 异常备注

每个节点建议记录：

- 订单 ID
- 节点类型
- 操作人
- 操作时间
- 位置或位置描述
- 备注

等待时长不允许人工直接填写，应通过“开始等待”和“结束等待”自动计算。

### 8.5 费用明细

平台不收款，但要记录费用结构。

建议字段：

- 基础报价
- 等待费
- 路桥费
- 停车费
- 其他附加费
- 最终总额
- 商家提交时间
- 乘客确认时间

最终总额应由系统自动汇总，不允许只手填总额。

### 8.6 发票记录

发票记录挂载在订单之下。

建议字段：

- 订单 ID
- 发票状态
- 发票类型
- 上传文件地址
- 上传时间
- 下载记录

### 8.7 异常记录

异常记录不形成独立工单系统，但必须可监管和可追溯。

建议字段：

- 关联对象类型
- 关联对象 ID
- 异常发起人
- 异常类型
- 异常描述
- 平台处理人
- 处理结果
- 处理备注
- 是否警告/封禁
- 创建时间
- 完成时间

## 9. 关键业务规则

### 9.1 报价窗口规则

平台采用按用车时间动态计算报价期的规则。

规则要求：

- 距离出发时间越近，报价窗口越短
- 距离出发时间越远，报价窗口越长
- 超过报价截止时间后不允许新增报价
- 有有效报价但乘客未选择时，需求单进入 `quoted_closed`
- 无有效报价时，需求单进入 `expired` 或提示重新发布

具体时间阈值放入后台配置，不在本文档中硬编码。

### 9.2 准入与审核规则

#### 乘客

- 允许轻注册
- 在发布正式需求、确认订单、申请发票等关键节点补充实名联系人信息

#### 商家

- 审核通过前不可报价和接单
- 必须提交企业主体信息、营业执照、服务资质、联系方式、车队信息
- 审核不通过后允许补充资料重新提交

#### 司机与车辆

- 由商家内部维护
- 平台支持抽查与监管
- V1 不开放司机独立入驻
- 数据模型预留未来个人司机扩展口

### 9.3 权限规则

#### 商家管理员 / 车队队长

可操作：

- 商家主页
- 资质资料
- 车辆司机管理
- 报价
- 订单
- 发票
- 成员权限

#### 普通司机

可操作：

- 查看被指派任务
- 更新履约状态
- 提交必要备注

不可操作：

- 对外报价
- 修改商家主页
- 管理成员和车辆

#### 平台后台用户

可操作：

- 审核
- 监管
- 配置
- 留痕

不可直接参与：

- 商家订单履约
- 费用录入

### 9.4 取消与关闭规则

#### 需求单取消

- 未确认商家前，乘客可取消需求单
- 已确认商家后，转入订单取消或异常记录流程

#### 报价撤回

- 乘客确认前，商家可撤回报价
- 乘客确认后，不可无痕撤回

#### 订单取消

- 已指派司机后，不允许无记录取消
- 必须记录取消原因、发起方、时间和处理备注

#### 超时关闭

- 无报价超时关闭
- 已有报价但长期未确认，可自动关闭或进入人工关注列表

### 9.5 费用留痕规则

- 报价金额与最终结算金额分开保存
- 等待费、路桥费、停车费、其他附加费单独记录
- 最终总额自动汇总
- 乘客确认表示“费用留档”，不表示线上付款

### 9.6 发票规则

- 发票仅在乘客提出需求时触发
- 发票由商家开具并上传
- 平台记录上传时间和关联订单
- 乘客在订单内下载发票
- V1 不做复杂开票审批流

### 9.7 异常监管规则

- 前台提供标准化异常报备入口
- 后台记录处理过程、责任判断、处理结果和备注
- 严重异常支持警告、限制、封禁
- V1 不建设完整仲裁中心

### 9.8 商家展示规则

- 商家主页必须包含公司介绍、资质、服务标签、车型、评分
- 车队展示以服务能力和可信度为核心
- “车找人”能力只承担展示和引流职责
- 真正交易统一回归需求单

## 10. 费用、发票与异常收尾设计

### 10.1 费用确认流

1. 商家在报价阶段提供预估报价
2. 行程结束后，商家录入实际费用明细
3. 系统自动汇总最终金额
4. 乘客确认费用留档

### 10.2 发票流

1. 乘客提出开票需求
2. 商家开具发票
3. 商家上传发票
4. 乘客在订单内下载

### 10.3 异常处理流

支持常见异常类型，例如：

- 司机未到
- 乘客未出现
- 联系不上
- 车辆不符
- 服务异常
- 需求临时变更
- 无法履约

处理流程为：

1. 用户或商家发起报备
2. 后台查看异常记录
3. 后台补充处理备注和结论
4. 必要时执行警告、限制或封禁

## 11. 测试策略与 V1 验收标准

### 11.1 必须跑通的核心链路

1. 商家入驻链路
2. 乘客发单链路
3. 多商家报价比选链路
4. 商家指派司机并完成履约链路
5. 费用录入与确认链路
6. 发票上传与下载链路
7. 异常报备与后台处理链路

### 11.2 测试层次

建议至少覆盖：

- 业务规则测试
- 接口与数据一致性测试
- 前端主流程测试
- 角色权限测试
- 异常场景测试

### 11.3 关键异常场景

建议至少覆盖：

- 无商家报价
- 商家撤回报价
- 乘客确认后取消
- 司机到达后乘客未出现
- 商家录入附加费
- 发票缺失或重复上传
- 商家被封禁后继续接单的权限拦截

### 11.4 V1 交付判定标准

满足以下条件时，可判定 V1 达到可交付状态：

- 商家入驻、审核、车队资料维护可用
- 三类主单型可正常发布
- 报价窗口规则生效
- 多商家报价可比选
- 订单状态机可完整跑通
- 等待状态可记录且可计算时长
- 费用明细可录入并自动汇总
- 发票上传与下载可用
- 异常报备与后台处理留痕可用
- 角色权限隔离正确
- 后台可执行审核、警告、封禁和查询
- 至少通过一轮端到端验收

### 11.5 非阻塞项

以下内容不作为 V1 上线阻塞条件：

- 在线支付
- 优惠券和会员体系
- 重型消息中心
- 复杂 BI 运营分析
- 完整仲裁/申诉系统
- 复杂商家装修和营销体系

## 12. 本文档结论

`悦程 V1` 应以“真实可跑通的商务接待撮合平台”为目标，优先完成：

- 商家准入与监管
